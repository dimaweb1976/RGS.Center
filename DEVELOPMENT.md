# RGS.Center — контекст разработки

Актуально на 24 июля 2026 года. Этот файл фиксирует состояние репозитория и
сопоставляет его с книгой BookStack «Проект.UAE-2601».

## Назначение

RGS.Center — серверное приложение роботизированного гамма-спектрометра.
Приложение планируется запускать как Windows-службу на NuvoPC. Оператор работает
с ним через браузер на LenovoPC.

Целевые обязанности приложения:

- опрос доступности и состояния оборудования;
- единая витрина текущих состояний и контрольных параметров;
- управление длительным сценарием автоматических измерений;
- хранение настроек и результатов в PostgreSQL;
- операторский и сервисный веб-интерфейс;
- аутентификация и разграничение ролей.

## Текущее состояние репозитория

- Java 26, Spring Boot 4.1.0, Maven, Thymeleaf.
- Реализованы главная страница и страница `/devices`.
- Реализован только опрос доступности камеры через `InetAddress.isReachable`.
- Состояние камеры хранится только в памяти.
- Включён планировщик Spring; опрос выполняется каждые 10 секунд.
- Есть лишь smoke-тест загрузки Spring-контекста.
- PostgreSQL, миграции, безопасность и прикладной сценарий измерения пока не
  подключены.

Основной код находится в `center/src`. Каталоги `backup_camera_*`, собранный JAR
в корне и журналы не являются исходным кодом и исключены из Git.

## Целевой сценарий измерения

Перед запуском:

1. Проверить сетевую доступность всех устройств.
2. Проверить начальное состояние механизмов.
3. Проверить контрольные параметры (готовность спектрометра и других модулей).
4. Параллельно включить высокое напряжение с контролем тока утечки и показать
   изображение камеры.
5. Сформировать и подтвердить список объектов.
6. Разрешить START только при сохранении всех условий готовности.

Для каждого объекта:

1. PLC забирает объект по координатам.
2. PLC переносит объект к считывателю кода; код считывается и валидируется.
3. PLC переносит объект на весы; вес считывается и валидируется.
4. PLC помещает объект в спектрометр.
5. GammaPro набирает спектр.
6. PLC извлекает и возвращает объект.
7. Результаты и состояние каждого шага сохраняются.

## Рекомендуемые ближайшие этапы

1. **Базовая модель устройств.** Заменить отдельный `CameraService` на реестр
   устройств, общий снимок состояния и независимые адаптеры оборудования.
2. **Конфигурация.** Вынести адреса, таймауты и интервалы опроса в типизированные
   `@ConfigurationProperties`; не хранить секреты в репозитории.
3. **PostgreSQL.** Добавить Spring Data JPA, Flyway и первую миграцию для
   настроек, измерений, объектов и журнала шагов.
4. **Оркестратор.** Представить сценарий измерения конечным автоматом с
   таймаутами, отменой, повторными попытками и безопасным восстановлением после
   перезапуска.
5. **Протоколы оборудования.** Реализовывать адаптеры после фиксации протоколов
   PLC, GammaPro, весов, считывателя, камеры и источника высокого напряжения.
6. **Веб-интерфейс и безопасность.** Сначала экран готовности и диагностики,
   затем очередь объектов, запуск/останов, прогресс и история; после этого роли
   оператора, инженера и администратора.
7. **Тестирование.** Unit-тесты автомата и адаптеров, интеграционные тесты БД,
   симуляторы устройств и один end-to-end сценарий без реального оборудования.

## Правила для следующей разработки

- Не связывать доменную логику напрямую с TCP/HTTP-клиентами устройств.
- Не считать `ping` доказательством готовности: доступность и рабочее состояние
  должны быть разными параметрами.
- Каждый внешний вызов обязан иметь таймаут и явный результат ошибки.
- Состояние длительного сценария должно переживать перезапуск приложения.
- Команда аварийной остановки и переход в безопасное состояние приоритетнее
  обычного исполнения сценария.
- IP-адреса и учётные данные задаются через внешний конфиг/переменные окружения.

## Команды разработчика

Из каталога `center`:

```powershell
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
.\mvnw.cmd clean package
```

Локально требуется JDK 26. Первый запуск wrapper скачивает Maven 3.9.16.
